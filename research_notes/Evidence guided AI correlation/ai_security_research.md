# AI assisted vulnerability analysis and correlation

## What does research actually support?

### Takeaway
The strongest relevant precedents combine LLM semantic inference with program analysis and external verification. They support letting AI propose missing models, retrieve relevant code and plan investigations; they do not establish that LLM judgement alone correctly correlates PHP static findings with runtime exploit evidence. The recommended system is an evidence-seeking investigator around a reliable analysis core, with an explicit unresolved outcome.

### Cited Findings
- **IRIS, ICLR 2025:** LLMs infer sources/sinks and provide contextual alert analysis; CodeQL performs repository-wide static analysis. Latest arXiv v3 evaluates 120 manually validated Java vulnerabilities: GPT-4 IRIS detects 55 against CodeQL's 27, with average false discovery rate improved by five percentage points. The result is vulnerability detection, not PHP support or SAST–DAST correlation. Earlier v1 says 69, so do not mix versioned metrics. The repository now has v2 code and points to v1 for original-paper code. — [Latest paper v3](https://arxiv.org/html/2405.17238v3); [repository](https://github.com/iris-sast/iris)
- **LLMDFA, NeurIPS 2024:** decomposes data-flow analysis into source/sink extraction, per-function summaries and path-feasibility validation. It delegates extraction to parser-backed code and feasibility to external expert tools such as SMT solvers. Incorrect local summaries can compound across functions, and language models struggle with satisfiability reasoning. Evaluation uses synthetic bug cases and Android applications; the aggregate precision/recall is not a PHP web-app correlation result. Its reusable lesson is decomposition plus checked tool outputs, rather than replacing a taint engine with prose. — [Published paper](https://chengpeng-wang.github.io/publications/LLMDFA_NeurIPS2024.pdf); [implementation](https://github.com/chengpeng-wang/LLMDFA)
- **LLMxCPG, USENIX Security 2025:** builds vulnerability-focused slices through CPG traversal and backward slicing, then uses those slices to fine-tune a model. Reported code reductions range from 67.84% to 90.93%. Its evaluated CWE set is memory-oriented, including buffer overflow, integer overflow, double free and use-after-free; no PHP experiment was located in the paper. It supports graph-informed context selection as a design pattern, not a ready-made PHP correlator or a claim that embedding similarity proves causation. — [Published paper](https://www.usenix.org/system/files/usenixsecurity25-lekssays.pdf)
- **Project Naptime, June 2024:** Google's framework equips the agent with a code browser, debugger and feedback from execution, and explores independent hypotheses. Its central lesson is that agents should interact with an environment and have automatically checkable outcomes. It substantially improved the authors' CyberSecEval2 memory-corruption performance; these benchmark outcomes are not evidence of reliable web exploit-to-code correlation. The article's phrase about absolute verification refers to tasks structured with a suitable verifier, not a universal theorem that every security finding has a perfect oracle. — [Project Zero architecture](https://projectzero.google/2024/06/project-naptime.html)
- **Big Sleep, November 2024:** extends the earlier work to variant analysis using previous fixes as starting points and demonstrates a SQLite stack-buffer-underflow finding with a reproduced assertion failure. The authors explicitly describe these results as experimental and say a target-specific fuzzer could be at least as effective. A concrete starting hypothesis, source access and observable failure explain much of its relevance; this is not a general promise of autonomous zero-day discovery. — [Project Zero writeup](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html)

### Inferences
- Our model should operate on small, relevant evidence bundles: one runtime observation, candidate source/sink paths, relevant include/call edges, branch conditions, protections and the exact code excerpts that support them. Whole-repository prompting is expensive and makes unsupported narrative easier.
- AI can propose that a previously unmodelled helper forwards an argument to a query operation, or that a routed JSON field is renamed before reaching a sink. Those proposals need parser/static checks, a checked function summary, runtime observation, or manual assessment before becoming reusable facts.
- Candidate retrieval should include multiple routes to discovery: metadata, code-graph neighbourhoods, observed traces and semantic retrieval. Semantic similarity supplies a lead, never an identity decision.
- Reusing CodeQL is not implied: IRIS's Java evaluation does not make it the PHP backend. Borrow the separation of model inference and checked analysis while retaining our own PHP parser/analysis infrastructure.
- Novel syntax or an unknown wrapper is more tractable than an entirely unknown vulnerability class: the first can enrich a known source/sink model; the latter needs a security property and observable violation before reliable confirmation.

### Gaps
- None of these inspected papers provides a measured end-to-end PHP SAST–DAST correlation accuracy guarantee. The proposed transfer must be evaluated on our applications and held-out cases.
- The literature's detection metrics do not quantify our issue-level merge errors, wrong source attribution, request-context mismatch or improper promotion of tentative runtime evidence.

## Where do LLMs and multiagent systems fail?

### Takeaway
Model reasoning and multiagent agreement are fallible inputs. Adding agents increases capability only when their work and external evidence are meaningfully complementary; reliability needs to be measured rather than inferred from agent count or self-reported confidence.

### Cited Findings
- **Project-scale vulnerability study, January 2026 preprint:** evaluates five LLM-based approaches and two traditional tools on 222 C/C++/Java vulnerabilities and 24 active projects, manually inspecting 385 warnings. It reports low recall, high false discovery rates, shallow interprocedural reasoning, misidentified sources/sinks, and substantial cost that can reach multi-hour/multi-day runs. This is a caution about concrete evaluated systems, not a claim that every current model behaves identically or that AI adds no value; the study also finds complementary detections. — [Primary paper](https://arxiv.org/html/2601.19239v1)
- **PrimeVul, 2024:** exposes noisy labels, code duplication and leakage in vulnerability datasets, and recommends chronological splits and paired vulnerable/patched evaluations. Its example 7B model scores 68.26% F1 on BigVul and 3.09% on PrimeVul under its settings. These are historical task-specific results, not contemporary PHP-agent scores. The useful lesson is that familiar benchmark success and balanced classification accuracy can conceal poor real-world security performance. — [Primary paper](https://arxiv.org/html/2403.18624v2)
- **Google agent-scaling study, January 2026:** compares 180 configurations across five architectures and four non-security task suites. Coordination helps parallelizable tasks but can degrade sequential ones; tool use and communication consume a fixed budget, and erroneous intermediate claims can propagate. Its numeric gains/losses should not be transferred to our engine. It rebuts the unconditional claim that adding agents guarantees better accuracy. — [Research team's explanation](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); [paper](https://arxiv.org/abs/2512.08296)
- **Anthropic workflow guidance:** distinguishes predefined tool/LLM workflows from agents directing their own tool use, recommends starting simply and adding complexity when needed, and emphasises environmental ground truth and stopping conditions. This is vendor engineering guidance rather than a security accuracy study. It supports selective routing of hard cases to an investigator instead of running a full agent conversation for every obvious match. — [Engineering article](https://www.anthropic.com/research/building-effective-agents)
- **Confidence calibration, UncertaiNLP October 2026:** six coding model variants on 365 contamination-aware problems show overconfidence across all 18 model/elicitation combinations under the study's strict scoring. Verbalised confidence can collapse or vary between runs, so it cannot be treated as a trustworthy pass probability without evaluation. Its task is generated-code correctness, not correlation; it supports caution rather than a claim that every confidence score is useless. — [Primary paper page](https://aclanthology.org/2026.uncertainlp-main.21/)
- **AgentDojo, NeurIPS 2024:** tests tool-using agents over untrusted content; its tasks show normal capability failures and successful indirect prompt injections. Source comments, HTML responses and scanner descriptions are analogous untrusted inputs for our system. **CyberSecEval 3** separately measures multiple risk/capability categories, including autonomous cyber operations; it is not a SAST–DAST matching benchmark. — [AgentDojo paper](https://arxiv.org/html/2406.13352v3); [CyberSecEval 3](https://arxiv.org/abs/2408.01605)

### Inferences
- Do not turn a model's “93% confident” into a calibrated probability of a correct link. Initially display evidence categories, contradictions and unresolved gaps. If later training a numeric scorer, fit and calibrate it against manually assessed links and evaluate calibration on held-out apps.
- A second agent reading the same snippet can repeat the same error. A useful critic must ask for missing causal edges, seek alternative candidate sinks and test a falsifiable hypothesis; votes are not independent observations.
- Non-deterministic is ambiguous here: usually the problem is incomplete information, state-dependent behaviour or unfamiliar semantics. Sampling variability in an LLM is another source of nondeterminism, not a remedy. Runtime races/timing variation need repeated trials and experimental controls, not merely a model explanation.
- Treat any embedded instruction in target source/response data as data. Agents should receive scoped code-read tools and structured test proposals; an execution controller checks target allowlists, redirects, methods, budgets and permitted operations. Do not give source-reading agents unrestricted shell or networking privileges.
- Logging prompts, selected snippets, tool versions and results permits audit, but pinning temperature alone does not guarantee identical provider output. Cache/replay completed evidence and preserve a deterministic final decision over that recorded evidence.

### Gaps
- No retrieved paper establishes that a specific number of agents or a named model yields best performance for our PHP codebase. A cost-matched single-investigator baseline is required.
- SWE-bench measures repository issue resolution, not code-to-exploit attribution. Its headline scores should not be used to justify this engine's security precision.

## What concrete AI contribution should our engine implement?

### Takeaway
Build a bounded investigation workflow for unresolved, conflicting and suspiciously weak matches. Its output is a checked evidence package or an explicit unresolved case, rather than a model-generated Confirmed label.

### Cited Findings
- The proposal below is an architectural inference from the tool-grounded principles above, particularly [Naptime](https://projectzero.google/2024/06/project-naptime.html), [IRIS](https://arxiv.org/html/2405.17238v3), [LLMDFA](https://chengpeng-wang.github.io/publications/LLMDFA_NeurIPS2024.pdf) and [agent workflow guidance](https://www.anthropic.com/research/building-effective-agents); it is not a published result for this engine.

### Inferences
1. **Retain a fast deterministic path.** Input validation, deployment identifiers, fingerprints, indexes and obvious matches remain reproducible. Even a unique metadata match must meet the required runtime-evidence tier before being called exploit-confirmed. AI should also audit a sample of apparently easy cases, since an early erroneous merge can hide ambiguity.
2. **Emit investigation tasks, not discarded findings.** Trigger on multiple candidates, missing routes, renamed inputs, unknown helper summaries, CWE disagreement, tentative DAST evidence, suppressed-code conflicts, stored flows or mismatched execution conditions. Preserve individual sightings before any irreversible issue grouping.
3. **Semantic investigator.** Retrieve relevant source slices; propose candidate mechanisms and missing graph edges. Each assertion carries finding IDs, exact source references, observed-versus-inferred status, supporting evidence, contradictions, alternatives and the next discriminating question. Unknown CWE stays allowed; the observed mechanism must survive even when classification is missing.
4. **Verification planner/executor.** Propose the smallest permitted observation that distinguishes hypotheses: inspect a relevant branch, repeat a baseline/test comparison under a recorded role/session, or request a narrowly scoped trace. The controller validates and executes approved tool operations. New payload shapes or request sequences can be proposed within the capability policy; new arbitrary executables should not be trusted because an LLM wrote them.
5. **Independent evidence critic.** Check whether the observations actually demonstrate the claimed effect and whether they identify this code location rather than another reachable sink. A trace establishes execution, not automatically data dependence or exploit causation. The critic can ask for more evidence but cannot manufacture a successful tool result.
6. **Deterministic evidence policy.** Promote only when both vulnerability verification and code attribution reach defined standards; retain potential relationships otherwise. Output structured reasons such as unresolved dynamic include, authentication unavailable, competing sink, no suitable verifier, configuration mismatch or budget exhausted.
7. **Stop with useful uncertainty.** Give each investigation a bounded tool-call/request/time/token budget. End when a link is supported, candidates contradicted, no informative permitted test remains or budget expires. Autonomous operation includes autonomously declining to assert an unsupported link.

Recommended phased scope: first repair current label/grouping semantics; then add one retrieval-and-hypothesis worker and a controlled verifier; add a separate critic if cost-matched evaluation shows value. Only expand discovery into wholly new vulnerability classes after mechanism-specific checks are credible. An unknown report format is an ingestion/schema problem; unknown code semantics is an analysis problem; unknown exploit mechanism is a verification problem. AI cannot solve all three simply by relaxing the matching gates.

Recommended evaluation includes deterministic baseline, corrected deterministic baseline, AI without new tool evidence, and AI with investigation tools. Keep discovered novel mechanisms separate from known-class correlation. Measure wrong links, attribution recall, abstention/coverage, incorrect confirmations, reproducibility across repeated runs, request/token costs and wall time. Use held-out applications and vulnerable/fixed pairs; include benign lookalikes, two same-CWE sinks behind one route, role/security-level differences, missing metadata and adversarial comments. The result to claim is measured incremental correct resolutions without increased wrong confirmations—not that autonomous multiagent architecture inherently understands every unseen vulnerability.

### Gaps
- Exact budgets, scoring thresholds and model choice need implementation trials; suggested architecture is not a performance promise.
- No code, application setup, scan or exploit test was performed in this research task.
