# Make AI investigate before confirming correlations

**Evolve the engine into an evidence-seeking investigation system: deterministic checks preserve correctness, AI proposes missing semantic relationships, and controlled observations decide whether a relationship is supported.** This addresses the mentors’ concern more directly than replacing rules with an LLM that guesses which findings belong together. The current engine already preserves ambiguity in useful cases, but early grouping and its definition of Confirmed can hide important distinctions. Those semantics need repair before agents receive their inputs. Relevant research supports combining model reasoning with program analysis and execution feedback; it does not demonstrate reliable end-to-end PHP SAST–DAST correlation. The practical first version needs one bounded investigator and a controlled tool executor, with additional agents justified through evaluation. This report combines a source-checked audit with primary research; no implementation changes, scans, exploit reproduction or new test execution were performed.

## Unfamiliar cases need evidence, not random decisions

“Deterministic versus nondeterministic” conflates different problems. An unfamiliar PHP wrapper or unresolved include usually means the engine lacks knowledge. A result that changes with authentication, security level or stored data is conditional on state. Timing variation, asynchronous execution and races introduce genuinely variable observations. LLM sampling adds another source of variability; it does not resolve the others. **The objective is adaptable investigation with reproducible acceptance rules**, rather than making the final matcher unpredictable.

The current engine joins metadata supplied by scanners. Its schema already carries source traces, sinks and conditions, but matching mainly uses CWE family, parameter, location, route and selector. Consequently, richer reasoning can begin with evidence already present, instead of assuming every improvement needs a new model. A route and CWE are useful retrieval clues; they do not establish that one specific operation caused the observed vulnerability. ([Current schema](/Users/ntbnaren7/Dev/cyberforge-sast-dast/common/finding.schema.json:40), [Matcher](/Users/ntbnaren7/Dev/cyberforge-sast-dast/correlator/correlate.py:109))

Research offers a consistent architecture precedent. IRIS combines LLM-inferred source/sink specifications and contextual filtering with CodeQL analysis. Its latest version reports detecting 55 of 120 manually validated Java vulnerabilities, compared with 27 for its CodeQL baseline. That is a Java vulnerability-detection result, not a PHP correlation score. LLMDFA decomposes analysis into extraction, function summaries and feasibility checking, using external tools for parts that models handle unreliably. These studies support **AI-generated hypotheses checked by analysis**, rather than trusting a narrative about a data flow. ([IRIS v3](https://arxiv.org/html/2405.17238v3), [LLMDFA](https://chengpeng-wang.github.io/publications/LLMDFA_NeurIPS2024.pdf))

Google’s Project Naptime similarly equips agents with code browsing, debugging and execution feedback. Its demonstrations have externally checkable outcomes in structured tasks; that does not mean every web vulnerability has a perfect verifier. Big Sleep demonstrates experimental variant analysis around SQLite, with the authors explicitly cautioning about the scope of the result. Conversely, a 2026 project-scale study reports shallow interprocedural reasoning, incorrect source/sink identification and expensive runs in evaluated LLM systems. **The literature motivates tool-grounded assistance, not guaranteed autonomous understanding.** ([Naptime](https://projectzero.google/2024/06/project-naptime.html), [Big Sleep](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html), [Project-scale study](https://arxiv.org/html/2601.19239v1))

The useful AI contribution is therefore specific: recover a renamed input through a wrapper, examine an unfamiliar protection, identify a missing caller or include edge, consider alternative sinks, and choose a test that separates competing explanations. An entirely new vulnerability mechanism is harder. It needs a security property and observable violation, not simply an unfamiliar description that a model can classify.

## Preserve distinctions before improving the matcher

The audit confirms several structural risks in the existing implementation. These are deductions from the rules, not claims that every corresponding failure has already occurred on a live application. The attachment’s reported 67 passing tests were not rerun during this research.

| Current behaviour | Why it can mislead | Recommended change |
|---|---|---|
| SAST union-find merges overlapping inputs within one family/file/function | Transitive relatedness can merge separate sink-level bugs | Preserve observations; establish bug identity after attribution |
| DAST groups without method or input location | GET/query and POST/body can represent different handlers | Preserve request occurrences and configuration; merge only with supporting evidence |
| Any attached runtime evidence yields Confirmed | Tentative alerts inherit a stronger-looking label | Separate exploit verification from code attribution |
| Suppressed-code matches become separate conflicts | Runtime findings leave the actionable issue list | Keep the runtime issue visible with the disagreement attached |
| Matching lacks required deployment identity | Correct-looking paths can join different builds | Record source/deployment/configuration provenance |

The SAST grouping rule does not compare sink identity or execution conditions. Its transitive union can connect findings with inputs `{id}`, `{id,name}` and `{name}` despite no direct overlap between the first and last. DAST grouping similarly excludes method, input location and verification. **Exact repeated-observation deduplication is appropriate early; semantic merging of underlying bugs should happen later.** Uncertain “possibly related” edges should not become unrestricted equivalence classes. ([SAST grouping](/Users/ntbnaren7/Dev/cyberforge-sast-dast/correlator/correlate.py:141), [DAST grouping](/Users/ntbnaren7/Dev/cyberforge-sast-dast/correlator/correlate.py:166), [Group attachment](/Users/ntbnaren7/Dev/cyberforge-sast-dast/correlator/correlate.py:254))

The current label becomes Confirmed when runtime evidence is attached, irrespective of its verification tier. Introduce independent axes: runtime verification such as suspected, validated or inconclusive; attribution such as candidate, supported, ambiguous or contradicted. A demonstrated runtime weakness with two plausible code locations remains runtime-validated but attribution-ambiguous. A plausible static link to a tentative runtime alert is correlated, not exploit-validated. Preserve the PRD’s labels as a derived view and document their meaning; do not silently reinterpret historical reports. ([Label construction](/Users/ntbnaren7/Dev/cyberforge-sast-dast/correlator/correlate.py:283))

Suppression cannot overrule an observed runtime claim by itself. The current branch records a conflict and continues without creating a Runtime only issue. Either side can be wrong: a suppression can be stale, or an alert can be false. Retain both, trigger investigation and leave the unresolved issue visible. Likewise, report-level overlap is not proof that source and runtime describe the same deployment; record application revision or digest, deployed source mapping, role and relevant security configuration. ([Conflict handling](/Users/ntbnaren7/Dev/cyberforge-sast-dast/correlator/correlate.py:269), [Deployment diagnostic](/Users/ntbnaren7/Dev/cyberforge-sast-dast/correlator/correlate.py:290))

CWE mapping also needs nuance. The existing table collapses CWE-943 into SQL injection and PHP include control into path traversal. MITRE defines CWE-943 broadly enough to include SQL, LDAP and XPath mechanisms; CWE-98 and CWE-22 can relate without being identical. Preserve original classifications and use broader compatibility to retrieve candidates. Require mechanism and context before accepting identity. Missing metadata should remain unknown, while an explicit contradiction should count against a candidate. An incomplete method list is not the same as a verified POST-only handler confronted with a GET request. ([Current mapping](/Users/ntbnaren7/Dev/cyberforge-sast-dast/common/cwe_families.json:1), [CWE-943](https://cwe.mitre.org/data/definitions/943.html), [CWE-98](https://cwe.mitre.org/data/definitions/98.html), [CWE-22](https://cwe.mitre.org/data/definitions/22.html))

## Agents should acquire discriminating evidence

Retain a deterministic controller for validation, candidate retrieval, budgets and final transitions. Straightforward cases stay on a fast path, subject to evidence requirements. Ambiguous, unmatched, contradictory and weakly verified cases enter an investigation queue. Candidate retrieval should combine metadata, include/call neighbourhoods, existing traces and semantic search; a true cause excluded from retrieval cannot be recovered by an excellent final judge. A graph of typed relationships can live in ordinary indexed records—this does not require a graph database.

The **semantic investigator** receives one bounded case packet: atomic observations, deployment identity, relevant request details, candidate source paths, conditions and artifacts. It retrieves exact snippets and returns competing hypotheses, cited source locations, assumptions, counterevidence and the next question. A proposed edge such as “external `q` becomes helper `$term`” remains inferred until checked against assignments, calls or execution evidence. Context should follow relevant graph paths rather than dumping the entire repository into a prompt.

The **verification planner** turns the unresolved question into an experiment: a baseline, the controlled change, predictions under each hypothesis, evidence to capture, reset instructions and stop conditions. A deterministic executor performs configured local HTTP/browser/trace operations. The model does not receive unrestricted shell access or mark its own observations verified. For the MVP, investigator and planner can be one agent loop; splitting them is worthwhile only when separate contexts or responsibilities improve results. A later read-only **evidence reviewer** challenges alternate explanations and missing controls. It can request evidence or reject an assertion; agreement among agents is not evidence of execution.

For example, suppose `/search.php` accepts `q`, and two SQL operations in one handler use it: a count query and a results query. Both have CWE-89, the same route and parameter. The existing grouping can collapse them before investigation. The improved engine retains two operation identities. The investigator traces each path and predicts which conditions execute each operation. The planner requests a controlled comparison and, when available, narrow execution evidence. If both operations execute, a function hit or generic database error still cannot identify the responsible operation. The outcome must remain ambiguous unless operation-specific influence and security behaviour distinguish the candidates. This is the standard we want agents to enforce, not explain away.

Begin with small, explicit per-case caps on rounds, requests, tool calls, time and tokens; exact values require trials. Stop after adequate evidence, contradicted candidates, unavailable prerequisites or exhausted budget. Preserve unresolved reasons such as authentication failure, competing sink, unknown include or unavailable verifier. Cache reusable code analysis by source revision, and keep model/version, prompt and tool transcripts for replay. **Autonomy includes deciding that available evidence is insufficient.** Vendor guidance favours simple workflows before added agent complexity, and controlled agent studies show coordination benefits depend on task structure and budget. Neither establishes that three agents outperform one investigator for our task. ([Agent engineering guidance](https://www.anthropic.com/research/building-effective-agents), [Agent-scaling research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/))

Target source, comments, HTML and scanner text are untrusted data. Agents need read-only evidence tools and a scoped executor with destination/redirect checks, permitted actions and credential redaction. Structured output validates shape, not truth. A second model repeating an injected instruction is not independent verification. AgentDojo demonstrates both ordinary task failures and indirect prompt injection in tool-using systems; its domains differ, but the trust-boundary lesson applies. ([AgentDojo](https://arxiv.org/abs/2406.13352))

## Runtime evidence strengthens attribution without universal proof

Evidence should advance through explicit support categories: metadata compatibility, contextual static path, observed execution, observed input influence, and validated security outcome with supported attribution. These are not calibrated probabilities. A static path can be infeasible; an executed line does not establish data dependence; a marker in a query can be safely bound data. A model’s “95% confident” cannot substitute for any missing step.

Provide two capability tiers. **Source-plus-HTTP mode** works without modifying the unseen target and can support links through checked source paths and controlled behaviour, with stated limits. **Instrumented local mode** adds request-scoped observations when extensions/hooks are available and permitted. The engine must not secretly depend on changing the judges’ environment. Xdebug function traces and coverage are plausible tools for selective ambiguous cases, not complete dynamic-taint analysis. Trace call sites and configurable arguments can narrow candidates; missing observations require known collection scope before they become counterevidence. ([Xdebug tracing](https://xdebug.org/docs/trace), [Xdebug coverage](https://xdebug.org/docs/code_coverage))

PHP’s include scope makes this distinction concrete: an included file inherits variables from its inclusion location, so a loaded-file relationship alone cannot reconstruct the value flow. `get_included_files()` supplies a set of loaded files, not repeated execution history or taint. OpenTelemetry likewise needs instrumentation and application support; its PHP automatic setup requires PHP 8+, Composer and libraries, and the extension alone produces no traces. Generic spans do not automatically identify statement-level security sinks. ([PHP include semantics](https://www.php.net/manual/en/function.include.php), [Included-files API](https://www.php.net/manual/en/function.get-included-files.php), [OpenTelemetry PHP](https://opentelemetry.io/docs/zero-code/php/auto/))

Mechanism-specific outcome checks remain necessary. Compare baseline, control and test observations instead of treating every database error as SQL injection. For XSS, text reflection is not browser execution. For stored XSS, preserve the writer request, record/entity linkage, reader workflow, render location and browser observation; matching a write route alone is insufficient. Record security level, role, valid session and relevant data state. Repeat and interleave observations where timing or background changes create noise, and report sample counts rather than invented statistical certainty. Comparing an upstream fixed version strengthens a specific hypothesis, but changed behaviour can also result from broken functionality; even interventions require controls. ([OWASP SQLi testing](https://owasp.github.io/www-project-web-security-testing-guide/stable/4-Web_Application_Security_Testing/07-Input_Validation_Testing/05-Testing_for_SQL_Injection), [OWASP stored-XSS testing](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/07-Input_Validation_Testing/02-Testing_for_Stored_Cross_Site_Scripting/))

The schema should become an extensible evidence contract. Keep required observation identity, producer/version, deployment/run identity, timestamps, locations, artifact references and verification state. Add typed optional evidence for request/attempt IDs, method and exact input occurrence, workflow/session profiles, original source statements, branch assumptions, controls and collection completeness. Distinguish observed, inferred and proposed relationships. Keep raw scanner classifications and allow unknown/provisional CWE with an explanation. SARIF property bags offer a precedent for extensions without abandoning a stable core. ([SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html))

An unknown report format is an ingestion problem; unfamiliar code semantics is an analysis problem; a novel weakness is a verification problem. Accepting an unfamiliar finding prevents data loss, but cannot create an observation that scanners never made. AI can propose a new hypothesis or verifier recipe, yet unsupported recipes stay experimental. The final policy checks that the required artifacts exist and support the claim; where outcome interpretation itself is uncertain, the result remains inconclusive rather than acquiring certainty from a valid JSON response.

## Evaluate each added capability against a corrected baseline

The immediate implementation sequence should repair evidence identity and statuses, add one read-only investigator, then add adaptive verification. A separate reviewer comes last. This separates reliability improvements from AI uplift and keeps the hackathon focused on correlation. The following evaluation is a handoff plan for the teammate, not work performed here.

| Experimental arm | Change | What the comparison answers |
|---|---|---|
| A | Current engine | What does the existing system actually resolve? |
| B | Corrected grouping, states and provenance | How much improves without AI? |
| C | B plus semantic investigator | Does AI recover missing relationships from existing evidence? |
| D | C plus controlled adaptive observations | Does investigation resolve genuine uncertainty? |
| E | D plus independent reviewer | Does multiagent separation justify its cost? |

Compare D and E under matched tool/request/token budgets, alongside any unrestricted comparison. Measure candidate recall, correct final attribution over assessed linkable bugs, wrong accepted links, false confirmations, overmerges, oversplits, unresolved coverage, duplicate stability and runtime/model cost. **Precision without coverage is misleading:** accepting one easy link is not equivalent to solving most of the benchmark. Show raw numerators and denominators, and plot error risk against accepted coverage. Calibrate numeric scores only with adequate independently assessed data; ordinal evidence tiers are more honest initially. Selective-classification research formalises the risk–coverage tradeoff, but does not confer statistical guarantees on uncalibrated LLM percentages. ([Selective classification](https://arxiv.org/abs/1705.08500))

Reserve an application before tuning prompts or rules. Include two sinks behind one route, same-name query/body inputs, conditional includes, helper renaming, stored workflows, changing roles, transient errors, unknown classifications, build mismatch, protected code and hostile instructions embedded in comments or responses. Use semantics-preserving renames to challenge memorisation; use vulnerable/fixed versions as distinct controls. Public labs alone are insufficient evidence of generalisation because models can have seen their source. PrimeVul documents duplication, noisy labels and evaluation leakage in vulnerability datasets; its methodological warning is relevant even though its task differs. ([PrimeVul](https://arxiv.org/abs/2403.18624))

Replay recorded evidence to isolate model decision variability, and separately rerun reset application cases to measure environmental variability. Do not use a model explanation or another model’s approval as the answer key. The most convincing demonstration is an old ambiguous case, competing hypotheses, a selected discriminating test, the recorded result and an evidence-supported resolution—or an explicit unresolved outcome. No research reviewed establishes an uplift for this engine yet; that becomes our measured contribution.

## Conclusion

The strongest pitch is: **“Our engine uses deterministic checks for fast matching, then AI investigates unresolved relationships and selects bounded tests. It links findings when the evidence supports the same root cause and preserves uncertainty when it does not.”** This describes a useful autonomous system without claiming universal vulnerability discovery or formal causal proof.

The distinctive contribution is an investigation record that makes every accepted link and every abstention inspectable. A smaller system that demonstrably resolves difficult cross-file cases is more defensible than a larger agent hierarchy whose confidence cannot be traced to observations. The engineering question becomes which additional evidence changes the decision—not how many agents agree with it.
