# Choose PHP targets that challenge correlation

**Start with DVWA, add OWASP Mutillidae II early, and reserve a reviewed subset of WackoPicko for an unseen-style evaluation.** Together they offer direct PHP entry points, conditional includes, shared variables, helper methods and multi-step workflows. Supplement them with selected NIST PHP cases to validate the custom taint analysis, then test specific historical vulnerabilities in phpMyAdmin and osTicket against their fixed counterparts. This is a stronger evaluation strategy than finding one application with the largest vulnerability menu. The recommendations below follow a broad review of upstream repositories, source files, official project pages, deployment definitions and vulnerability advisories; they are not an exhaustive census of the internet. **No application was installed, started or scanned during this research.** Documented Docker support is therefore a setup lead, not a verified successful run on our machine. Research date: 31 October 2026.

## Three applications cover different correlation challenges

The most useful initial collection is small enough to understand manually but varied enough to expose application-specific assumptions. The following ranking is our assessment of suitability for this engine, rather than a claim that every documented vulnerability will reproduce on a current runtime.

| Candidate | Recommended role | What it contributes | Setup and licensing evidence | Main limitation |
|---|---|---|---|---|
| **DVWA** | First end-to-end baseline | Conditional includes, shared include scope, vulnerable/protected variants | Upstream Docker Compose; PHP/MariaDB; GPL-3.0 | Runtime security level changes which code executes |
| **OWASP Mutillidae II** | Cross-file integration gate | Query-parameter dispatch, shared handlers, object/method flows | Maintainer Docker projects; PHP/database stack; GPL-3.0 | More configuration and authentication state |
| **WackoPicko** | Conditional held-out application | Research-oriented scanner benchmark, helper files, multi-step cases | Upstream Docker instructions; MIT | PHP 5-era packaging and obsolete exercises |
| **XVWA** | Optional procedural supplement | Includes, SQLi, XSS, command injection, redirects | Source and manual setup; GPL-3.0 | Archived; current runtime compatibility unverified |
| **Pikachu** | Optional category supplement | Broad PHP vulnerability exercises | Dockerfile; Apache-2.0 | Upstream marks PHP project asleep; PHP 7-era stack |
| **bWAPP** | Optional broad legacy supplement | Extensive vulnerability menu | Author-owned SourceForge distribution | Old source/setup; exact license and modern compatibility need checking |

Repository and setup evidence supporting this comparison comes from the canonical [DVWA repository](https://github.com/digininja/DVWA), [Mutillidae repository](https://github.com/webpwnized/mutillidae), [WackoPicko repository](https://github.com/adamdoupe/WackoPicko), [XVWA repository](https://github.com/s4n7h0/xvwa), [Pikachu repository](https://github.com/zhuifengshaonianhanlu/pikachu) and [bWAPP project](https://sourceforge.net/projects/bwapp/).

**DVWA is the best first target.** Its upstream project supplies source, Docker Compose and a modern PHP image definition. The inspected Dockerfile uses `php:8-apache`; the Compose setup pairs the app with MariaDB. That removes some legacy setup uncertainty, although actual build and architecture compatibility remain untested here. DVWA is a community training application; it should not be described as an official OWASP project merely because it teaches OWASP vulnerability categories. ([Installation guidance](https://github.com/digininja/DVWA/blob/master/README.md), [Dockerfile](https://raw.githubusercontent.com/digininja/DVWA/master/Dockerfile), [Compose](https://raw.githubusercontent.com/digininja/DVWA/master/compose.yml))

DVWA already exercises the exact concern about cross-file scanning. In its file-inclusion module, `fi/source/low.php` takes request input and assigns it to the shared `$file` variable; the parent `fi/index.php` subsequently performs the include. The input source and sensitive operation therefore sit in different files, connected through PHP include scope. This is a useful early test of our own analysis, rather than another isolated unsafe query. File inclusion must still be classified according to its actual mechanism; it should not automatically be counted as the PRD's path-traversal category. ([Included implementation](https://raw.githubusercontent.com/digininja/DVWA/master/vulnerabilities/fi/source/low.php), [Parent entry point](https://raw.githubusercontent.com/digininja/DVWA/master/vulnerabilities/fi/index.php))

Its SQL injection entry point introduces another essential test: the same URL selects different implementation files based on security state, and the medium level changes the form method to POST. The low implementation constructs a query from request input; the impossible implementation uses prepared statements and numeric validation. We should test both, while recording the selected security level, database backend and request method. Otherwise a runtime finding could be incorrectly linked to every statically vulnerable implementation behind the URL. ([Dispatch](https://raw.githubusercontent.com/digininja/DVWA/master/vulnerabilities/sqli/index.php), [Low implementation](https://raw.githubusercontent.com/digininja/DVWA/master/vulnerabilities/sqli/source/low.php), [Protected implementation](https://raw.githubusercontent.com/digininja/DVWA/master/vulnerabilities/sqli/source/impossible.php))

**Mutillidae II should be an early integration target.** It is an actual OWASP project, with source and two maintainer-owned Docker deployment projects. Source now lives under `src/`, so older tutorials can describe outdated paths. Its current packaging involves several services, including database and LDAP components; this is a larger environment than DVWA. ([OWASP project](https://owasp.org/projects/mutillidae-ii), [Source](https://github.com/webpwnized/mutillidae), [Prebuilt-image deployment](https://github.com/webpwnized/mutillidae-dockerhub), [Local-build deployment](https://github.com/webpwnized/mutillidae-docker))

The valuable correlation case is `index.php?page=user-info.php`. The front controller loads shared classes and application state, then dispatches using the `page` parameter. The selected file reads inputs and calls `SQLQueryHandler::getUserAccount`, which constructs a query and passes it through a database handler in another file. Security-level state changes its protections. Our route identity must therefore preserve routing parameters, and our data-flow model must cross method and object boundaries. Matching only pathname and CWE would be inadequate. ([Front controller](https://raw.githubusercontent.com/webpwnized/mutillidae/main/src/index.php), [Input and helper call](https://raw.githubusercontent.com/webpwnized/mutillidae/main/src/user-info.php), [SQL helper](https://raw.githubusercontent.com/webpwnized/mutillidae/main/src/classes/SQLQueryHandler.php))

**WackoPicko is a useful held-out candidate only after a setup check.** Its researcher-owned repository describes a PHP application used for scanner evaluation and documents vulnerable endpoints, parameters and test accounts. Cases include SQLi, reflected/stored XSS, command injection and directory traversal. Actual source connects a search entry point to included helpers and picture methods. However, the Dockerfile uses `tutum/lamp`, PHP 5 packages and `/etc/php5`; the README includes Flash and null-byte exercises that cannot be assumed reproducible today. Reserve compatible, manually assessed cases rather than treating its entire menu as a current benchmark. ([Repository and case documentation](https://github.com/adamdoupe/WackoPicko), [Dockerfile](https://raw.githubusercontent.com/adamdoupe/WackoPicko/master/Dockerfile), [Search source](https://raw.githubusercontent.com/adamdoupe/WackoPicko/master/website/pictures/search.php))

## NIST cases isolate taint-analysis mistakes

Full applications are necessary for evaluating scanning and correlation, but they make individual analysis failures difficult to diagnose. NIST's Software Assurance Reference Dataset supplies separately named PHP suites with case metadata. These are **synthetic test collections, not deployable web-shop replacements and not a PHP edition of Juliet**. Their metadata provides a starting point for assessed cases; it does not eliminate the need to inspect dependencies and semantics. ([NIST suite catalog](https://samate.nist.gov/SARD/test-suites?o=desc&s=name))

**Suite 103 contains 42,212 PHP cases**, including XSS, SQLi and URL-redirection cases with candidate-good/bad metadata. **Suite 114 contains 248,592 cases** covering XSS and SQLi, with source, data-flow, sanitisation, context and sink descriptions. Their size is not a reason to run every generated case during the hackathon. A small reviewed subset can check whether our scanner distinguishes unsafe flows from prepared queries and relevant protections. Download contents, redistribution terms and runtime harness requirements were not verified in this research. ([Suite 103](https://samate.nist.gov/SARD/test-suites/103), [Suite 114](https://samate.nist.gov/SARD/test-suites/114))

**Suite 115 contains 20 XSS data-flow cases**, including globals, returned references, dynamic calls and magic accessors. These fit the concern about PHP semantics particularly well: they can reveal unsupported constructs before a complete application hides the failure behind routing or authentication. This suite is not a balanced safe/unsafe collection; the inspected cases are candidate bad. Keep unsupported cases visible as limitations, and avoid teaching the engine to rely on benchmark filenames or labels. ([Suite 115](https://samate.nist.gov/SARD/test-suites/115))

## Historical fixes add realistic positive and negative controls

Training labs demonstrate breadth; specific historical bugs in real PHP applications test whether the engine handles less artificial code. Two cases have especially useful upstream patches. Neither provides an application-wide answer key, and a patched release is a negative control only for the particular patched issue.

| Application and issue | Candidate vulnerable version | Fixed counterpart | Why it helps |
|---|---|---|---|
| phpMyAdmin SQLi, CVE-2020-26935 | 4.9.5 or 5.0.2 | 4.9.6 or 5.0.3 | Controller flow and application-specific query protection |
| osTicket reflected XSS, CVE-2023-1315 | 1.16.5 | 1.16.6 | Handler/template attribution and authenticated workflow |
| Optional phpMyAdmin file inclusion, CVE-2018-12613 | 4.8.1 | 4.8.2 | Include/path validation, with existing Vulhub environment |

**phpMyAdmin's upstream advisory identifies the affected version ranges and exact SQLi fix.** The patch changes a controller and accompanying JavaScript, adding query-signature verification before a submitted SQL clause is used. This is valuable precisely because the protection is more application-specific than a familiar escaping function. The official Docker project supports versioned PHP/database deployments, but old tag availability and local startup have not been tested. Pin application, PHP and database versions together. ([Vendor advisory](https://www.phpmyadmin.net/security/PMASA-2020-6/), [Exact fix](https://github.com/phpmyadmin/phpmyadmin/commit/d09ab9bc9d634ad08b866d42bb8c4109869d38d2), [Official Docker project](https://github.com/phpmyadmin/docker))

**osTicket's upstream XSS patch spans an AJAX handler and an included staff template**, adding integer conversion for parent identifiers. Release 1.16.6 explicitly includes it. This gives us a concrete input-to-template attribution case and a straightforward fixed-code comparison, though reaching the workflow requires authentication and suitable application state. Historical installation requirements must come from the relevant release rather than today's documentation. ([Upstream patch](https://github.com/osTicket/osTicket/commit/ec6043935b4e30b5c0dfa544e256717182808a2e), [Release](https://github.com/osTicket/osTicket/releases/tag/v1.16.6), [Historical documentation](https://docs.osticket.com/en/v1.16.4/))

Vulhub can reduce setup work for the optional phpMyAdmin 4.8.1 file-inclusion case. However, its fixture directory contains Compose/configuration rather than the complete application source. Scanning that directory with SAST would not analyse the PHP code running in the image. Obtain the exact deployed source and preserve the vendor's configuration-dependent exploitability conditions. Interpreter and webserver vulnerabilities elsewhere in Vulhub are not automatically suitable app-code correlation tests. ([Vulhub fixture](https://github.com/vulhub/vulhub/tree/master/phpmyadmin/CVE-2018-12613), [Vendor advisory](https://www.phpmyadmin.net/security/PMASA-2018-4/))

## Legacy alternatives broaden coverage but increase setup uncertainty

**XVWA** provides procedural PHP/MySQL examples including SQLi, XSS, command injection, file inclusion and unvalidated redirects. Its SQLi entry includes another file containing request-dependent logic, so it contributes useful structural diversity. The canonical repository is archived/read-only, and its Docker guidance points outside the main repository. Treat it as an optional legacy environment, not a guaranteed modern-PHP target. ([XVWA](https://github.com/s4n7h0/xvwa))

**Pikachu** offers broad coverage, including command execution, traversal and insecure redirects. Its source has straightforward form-to-operation cases with shared includes. However, upstream explicitly calls the PHP project old/asleep and directs users to a Java successor; the Dockerfile uses a PHP 7-era stack. **bWAPP** advertises more than 100 bugs, but its source browser and project metadata are old, and exact licensing and PHP compatibility were not established. Both can supply additional assessed cases if setup remains inexpensive. ([Pikachu](https://github.com/zhuifengshaonianhanlu/pikachu), [bWAPP](https://sourceforge.net/projects/bwapp/))

**OWASP Bricks and Peruggia** are legitimate historical PHP candidates, but their canonical release listings date to 2013 and 2010 respectively. **SQLi-Labs** is useful for specialised SQLi testing, not four-category validation; original lessons use obsolete `mysql_*` functions, and the reviewed PHP 7 update is a community fork. Verify the selected distribution's licensing before treating it as a redistributable fixture. ([Bricks](https://vwad.owasp.org/app/bricks/), [Peruggia](https://vwad.owasp.org/app/peruggia/), [SQLi-Labs](https://github.com/Audi-1/sqli-labs), [PHP 7 fork](https://github.com/skyblueee/sqli-labs-php7))

Some attractive search results should be excluded or deferred. OWASP Damn Vulnerable Web Sockets is PHP/MIT but needs WebSocket-aware testing. VulnLab has conflicting license signals: its license file says CC BY-NC-SA while its Dockerfile claims MPL, so it is not an unqualified open-source recommendation. Juice Shop uses Node.js, VulnerableApp and WAVSEP are Java, and the generic OWASP Benchmark repository resolves to BenchmarkJava. They cannot validate our current PHP SAST coverage. ([DVWS](https://github.com/interference-security/DVWS), [VulnLab license](https://github.com/Yavuzlar/VulnLab/blob/main/LICENSE.md), [OWASP vulnerable-app directory](https://vwad.owasp.org/), [VulnerableApp](https://owasp.org/projects/vulnerableapp), [Benchmark repository](https://github.com/OWASP/Benchmark))

## Build an assessed case set before claiming accuracy

The recommended sequence is to establish DVWA end-to-end results, introduce Mutillidae before the analyser becomes tailored to DVWA, and validate difficult PHP semantics with selected NIST cases in parallel. Then freeze detection logic for a compatible WackoPicko subset. Finally, assess the two real-application patch pairs. Reserving an application means avoiding tuning rules against its individual expected findings; a setup check and documented session configuration are still legitimate.

Each assessed case needs an application revision, matching deployed source, runtime configuration, role/session, endpoint, method, input, expected code location, evidence criteria and manually verified outcome. Security level is part of the case identity. DVWA's Compose uses a moving image tag, and Mutillidae's local build fetches moving source, so a local checkout cannot simply be assumed identical to container contents. Record exact revisions or inspect the deployed tree before measuring attribution. ([DVWA Compose](https://raw.githubusercontent.com/digininja/DVWA/master/compose.yml), [Mutillidae build](https://raw.githubusercontent.com/webpwnized/mutillidae-docker/main/.build/www/Dockerfile))

For scoring, distinguish assessed vulnerable cases, assessed protected cases and unassessed observations. Vulnerability-menu counts are not confirmed-pair counts; undocumented findings are not automatically false positives. Measure detection, correct attribution, wrong links, duplicate handling and total runtime separately. Do not count string reflection alone as XSS execution, or failed exploitation as proof of safety. These are evaluation recommendations, not claims that the applications have already supplied complete ground truth.

The practical implication is that a smaller set of carefully verified flows will make the demo more credible than a large unqualified vulnerability count. **DVWA plus Mutillidae should be the immediate application shortlist; the other targets add evidence only when their distinct cases are reproduced and their source-to-runtime correspondence is established.**
